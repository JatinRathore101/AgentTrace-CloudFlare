Request flow

sequenceDiagram
  participant UI as Run page
  participant API as POST /api/runs
  participant DO as TraceAgent (DO)
  participant AI as Workers AI via Gateway
  UI->>API: scenario + faults + model
  API->>DO: startRun(input)
  DO-->>API: runId (status running)
  API-->>UI: 202 { runId }
  DO->>DO: schedule(0, "executeRun")
  loop until final answer or maxSteps
    DO->>AI: messages + tools
    AI-->>DO: response, usage, tool_calls
    DO->>DO: insert llm span, run tools, insert tool spans
    DO-->>UI: setState(progress) over WebSocket
  end
  DO->>DO: detectors → findings, totals → runs row
  UI->>API: GET /api/runs/:id
  API->>DO: getRun(id)

Key design choices

  • Route handlers never touch SQLite directly. They call DO RPC methods through a stub (getAgentByName(env.TraceAgent, "default")). 🟡 verify helper name in phase 1
  • The agent loop runs inside the DO, triggered by this.schedule(0, "executeRun", { runId }), so POST /api/runs returns at once. 🟡 verify in phase 1; fallback ctx.waitUntil
  • Live progress: setState({ active }) → useAgent on the run page. Fallback: poll GET /api/runs/[id] every 1.5 s.
  • Everything Cloudflare-specific sits behind src/agent/*. The UI is plain Next.js and MUI.
